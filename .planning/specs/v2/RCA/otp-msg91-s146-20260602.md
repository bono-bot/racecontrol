## A2 — Inherited-issue catalogue
1. **Unofficial-gateway ban (CRITICAL, realised):** Evolution/Baileys violates WhatsApp ToS; re-pair cycling **banned** Reception #919059833001 on 2026-06-02. Root cause of the forced pivot.
2. **Send-failure semantics differ by layer (corrected):** V1 Rust returns a boolean `delivered`, no retry → silent OTP loss possible *there*. The V2 bono path is **NOT silent** — real `502 otp_vendor_failed` (phone-scrubbed, `registration-forwarders.ts:269,:297`) + identical-`200` on success (anti-enumeration, :318-321). The earlier "silent-200 on send-failure" premise was FALSE / refuted by bono's DIAGNOSE gate — **do NOT reintroduce.** Migration MUST PRESERVE the 502 + identical-200 (map MSG91 verify-failure → `otp_vendor_failed`).
3. **Committed credentials (item #2):** Evolution key + `jwt_secret` + `admin_pin_hash` plaintext across ~32 commits; + settings.json PAT/OAuth. Rotation = Captain/operator (can't be redacted from history → rotate-at-source + externalize).
4. **Server-direct egress vs CD-16:** V1 sends from Server with a Server-side WhatsApp credential — contradicts Bono-only-egress doctrine.
5. **Expiry/rate mismatch:** V1 5-min expiry + bono CD-13 limits vs MSG91 widget 15-min minimum + MSG91 resend limits — reconcile.
6. **Two-layer hash/TTL divergence (CRITICAL, foundational — A2.6, corrected):** the OTP boundary is verified in TWO places with DIFFERENT primitives — racecontrol `otp.rs` (**Argon2id** + recent-OTP-reuse window) vs coordinator REG-3 (**in-memory code → opaque `otp_verify_token_opaque`**, ≤5-min single-use, phone-bound; *not bcrypt*). A cutover touching one layer and not the other risks a verification split. Triggered directly by this migration → must converge before cutover.
7. **Kiosk debug-PIN bare-compare (A2.7, corrected):** `token_consume.rs:21` `pin == daily_pin` is a non-constant-time `==` on a `jwt_secret`-derived daily PIN. Auth-adjacent; real risk is forgeability-if-`jwt_secret`-leaks (→ item #2) + timing side-channel. **Confirm + fix in the same pass** (constant-time compare; the forgery risk closes with rotation).
8. **Code-ownership inversion vs typed contract (A2.8, grounded):** V2 bono *generates* the code (`generateOtpCode()` :250), stores it, `verifyOtp` compares; `evolution.ts SendOtpRequest{phone,code}` encodes this. The MSG91 widget **INVERTS** code-ownership (MSG91 gen+send+verify; bono does `verifyAccessToken`, holds no code). → `SendOtpRequest{phone,code}` is NOT the target; a NEW `packages/contracts/src/msg91.ts` (verifyAccessToken request/result, **no `code`**) is needed. `OtpDeliveryFailureSignal.cause=instance_not_open` is Evolution-specific → N/A for MSG91.
