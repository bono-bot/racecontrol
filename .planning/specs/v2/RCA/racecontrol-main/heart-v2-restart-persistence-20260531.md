## §2 — Inherited-issue catalogue (§S-61 V1 failure-modes + categories A-J)
- **Category: process-local state with no durability** (mock-heart parity). The ported `apps/mock-heart` held sessions in a JS in-memory map; the Rust port preserved that semantics verbatim (acceptable for a sandbox mock, a defect for a prod heart). This is the inherited failure-mode: *single-process volatile state survives no restart*.
- **Idempotency-on-redelivery** (already mitigated): ended sessions are *retained* in the map so re-delivered end/pause return 200 not 404 (`heart_v2.rs:188`). Persistence must preserve this property across restart.
- **No money-state inheritance:** `PodSession` (`heart_v2.rs:100-120`) carries no HOLD/debit/balance; `credits_debited` is init-0 and never mutated; `green_light_at` is a signal only. So none of the V1 billing/wallet failure-modes are inherited here.

## §3 — Past-bug disposition
- *In-memory loss on restart* — **root-caused, not previously patched.** It was a deliberate sandbox simplification in mock-heart (not-a-bug-in-context); becomes a real defect only when the Rust heart serves a live session. This RCA root-causes it (durability), not patches-forward.
- *No prior patched-only / unresolved bug* on this surface relevant to persistence. The session-surface itself shipped clean at `27d47dc4` (18/18 tests).

## §4 — V2-alignment delta
- V2 bug-free bar = first-INR e2e survives on a real pod. A heart restart mid-session (crash, OTA, OOM, panic-restart) currently drops the in-flight session → pod display + proxy lose their session reference → a customer mid-race is orphaned. **In-memory-only violates the bar.**
- Delta: add **durable write-through + boot rehydration**, keeping strict V1/V2 isolation (new v2db table; never read/write V1 tables). Source-of-truth on rehydrate = the durable store.

## §5 — V2-framed proposal
1. **New migration** `crates/v2-db/migrations/2026053118xxxx_heart_v2_sessions.sql` — table `heart_v2_sessions` mirroring `PodSession` (id PK, pod_id, household_id, profile_id, preset_id, lobby_id, state, tier, game, started_at, green_light_at, paused_at, pause_ms_total, credits_debited, created_at, updated_at). V2-isolated; no FK into V1.
2. **Write-through:** each mutator (`launch/pause/resume/switch_game/end`) UPSERTs the session row after the in-memory mutation, within the handler (lock released before `.await` per existing discipline — DB write happens after the `RwLock` write-guard drop, using a snapshot/clone of the mutated `PodSession`).
3. **Boot rehydration:** add `HeartStore::load(v2db) -> HeartStore` (or an async `rehydrate(&v2db)` after `AppState::new`) that reads all rows, repopulates `sessions`, and **relinks** `pod.current_session` for any pod whose live (non-ended) session references it. Called once at startup (`main.rs`).
4. **Crash-window analysis:** ordering = mutate-memory → write-DB. A crash between the two loses only that one DB write (the in-memory state is gone too on restart, so the lost write self-cancels — no torn state). Because **no money is held in the heart** (proxy owns wallet+402), the worst case of a missed write-through is a session that rehydrates one transition stale; the proxy's billing (driven by `green_light_at`/its own ledger) is unaffected. Acceptable; documented.
5. **Ended-session retention + prune:** persist ended sessions (idempotency) but prune rows older than a bounded window (e.g. 24h) on boot to keep the table from growing unbounded.
6. **Tests:** (a) write a running session → drop HeartStore → `load(v2db)` → assert session present + `state==Running` + `pod.current_session` relinked; (b) pause then restart → assert `Paused` + `pause_ms_total` preserved; (c) ended session survives for idempotency; (d) V1-isolation: assert no V1 table touched. In-memory SQLite fixture (`open_and_migrate_in_memory`).

**MMA Step 1 DIAGNOSE** (foundational pod-state-channel + DB-schema) to run before authoring — to stress write-through ordering, rehydration correctness (pod relink), and V1/V2 isolation across ≥5 OpenRouter models.
