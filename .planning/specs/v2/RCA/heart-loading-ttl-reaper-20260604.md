# §S-146 RCA — heart_v2 Loading-stale TTL reaper (#11)

**Date:** 2026-06-04 · **Author:** bono · **Boundary:** pod-state-channel / reconciler (foundational, billing-adjacent) · **Status:** built + cargo-tested, STAGED for Captain merge.

> **Produced + adversarially corrected via workflow `wf_2c413c5b-fec`.** The money-path adversarial pass returned **NEEDS_FIXES (high)** — the core design is SAFE (billing-neutral; TTL provably safe) but three corrections were applied before/in the code. **These override any contradictory text in the body below:**
>
> **Money-path SAFE (verified file:line):** a `Loading` session has `green_light_at=None` + `credits_debited=0` (`heart_v2.rs:355-362`); billing/green-light is granted only at `promote_to_running` / `reconcile_green_light`. So reaping a `Loading` session is **provably billing-neutral**. The new arm is placed **after** the `Some(GameState::Running) => Promote` arm, so a slow launch the agent has confirmed Running is **promoted, not reaped**.
>
> **TTL safety:** `LOADING_STALE_TTL = 600s` must exceed the max legitimate `launch_loading→promote` window. The full in-request worst case (all in `dispatch_launch_to_agent`, `game_launcher_ops.rs`) ≈ semaphore-acquire 30s + send-retry 3s + ACK 5s + verify 60s ≈ **~98s**, plus AC/Steam cold-start (30-120s). 600s is ~5× margin over the realistic ~120s worst case and strictly **below** `RECONCILE_SUSTAINED_ABSENCE=900s` (`heart_v2.rs:998`), so a slow-but-valid launch is never reaped and the Loading arm stays the more-specific case.
>
> **Three corrections applied:**
> 1. **Scope of the fix (RCA factual):** the age-based `Loading` arm closes the **dropped/dead in-request-task** case ONLY — the `launch_real` future aborted at the `.await` (`heart_v2.rs:807`) after `launch_loading` persisted `Loading` but before `promote`/`abandon`. It does **NOT** close "heart restart mid-dispatch": on restart `apply_loaded_sessions` forces every persisted `Loading` → `Running` (`heart_v2.rs:594-597`), so a restarted session is Running-without-green-light, handled by the rehydrate→Running + existing Promote/sustained-absence path, **never** seen by the age-arm.
> 2. **Plumbing:** the reconcile `acts` collection carries `pod_id` (not just `sid`) because `abandon_launch(&state, &pod_id, &sid, …)` requires it.
> 3. **Lock discipline:** `AbandonStale` is applied in a **SECOND pass after the heart write-guard is dropped** (`abandon_launch` is async + needs `&state`; holding `heart.write()` across `.await` is the banned lock-across-await pattern). It reuses `abandon_launch`'s **StopGame-before-fail_launch** ordering verbatim.
>
> **MTC (5/5 YES):** atomic (apply under one write-lock for the synchronous acts; AbandonStale in the post-guard pass) · TTL-bounded + auto-clearing (unlike MAINTENANCE_MODE) · behavioral-verify (pure matrix asserts the exact `ReconcileAct`) · single-target dry-run (the matrix test IS the dry-run) · written ordering contract (inherited from `abandon_launch`).
>
> **Known follow-ons (noted, not introduced by this PR):** StopGame is pod-wide + unkeyed (`heart_v2.rs:868-875`) — pre-existing launch_id-binding follow-on; the reaper preserves the FIFO ordering and does not worsen it. Optional `POST /heart/pods/{id}/force-free` manual override = separate later slice.
