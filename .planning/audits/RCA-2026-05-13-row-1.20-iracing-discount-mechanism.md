## 1. Boundary map

- `crates/racecontrol/src/api/pricing_routes.rs:117,124` — V1 returns `has_discount: bool` derived from `dynamic_price != price_paise` but does NOT accept game-context input; discount is happy-hour-style (time-window-only), not game-aware

**D. Walk-in fallback discount_ineligible flag**
- DoD §3.3 L48 + L341 — V2 requires `customer.discount_ineligible: bool` on Walk-In Guest 1+2 accounts; pricing engine must zero out happy-hour, iRacing, AND bonus-credit incentives for `discount_ineligible: true`

## 4. V2-alignment delta

V2 iRacing-discount substrate must encode 4 doctrine elements:

**A. Game-context-aware pricing.** `POST /billing/start` accepts `game_context: Enum`. Pricing rule resolution receives game_context as input. Wallet-debits per-tick read locked-in pricing-rule + game_context from `billing_sessions.pricing_lock`.

**B. Multi-discount stacking policy.** Single `applied_discount` per debit row, computed as `max(happy_hour_pct, iracing_pct)`. Rule encoded as pure function `resolve_discount(time: IST, game_context: GameCtx, customer: Customer) -> AppliedDiscount`; testable.

**C. Per-debit audit columns.** `wallet_debits` schema adds `{discount_applied: TEXT, discount_pct: REAL, game_context: TEXT, locked_rate_paise: INTEGER}`. Each debit row stamps which rule fired. Composes-with §S-242 Q-1.14 DPDP audit-table retention doctrine (locked-rate trail).

**D. Tier 1 vs Tier 2 iRacing pathway.** Kiosk game-selection is the PRE-CONDITION for both:
- Tier 1 (full-skeleton, v2.1+): game_context=iRacing_T1; telemetry presence + active session → 20% applies; iRacing-active-fleet signal (RCA-row-1.19 Phase 2) is mandatory
- Tier 2 (desktop-workaround, v2.0): game_context=iRacing_T2_desktop; Kiosk pre-select sufficient; no telemetry gate; 20% applies regardless of telemetry

**E. discount_ineligible early-zero guard.** Pricing engine reads `customer.discount_ineligible` BEFORE deeper-of resolution; if true → `applied_discount = None`, `discount_pct = 0.0` (NOT default + happy-hour-still-applies); zero ALL discount-class incentives.

**Named gap (R2):** V1 pricing engine is time-axis-only (happy-hour). V2 makes it game × customer × time-axis. The substrate-PR moves the pricing rule from single-input to 3-axis input; corresponding spec MUST land at `comms-link/v2-skeleton/...` defining the rate-table evolution.

## 5. V2-framed proposed change

**Phasing (3 sub-phases; total ~150-200 LOC server-side; composes with Phase 2-A rate-table):**

**Phase 1 — billing/start game-context schema + Tier 2 desktop-workaround pricing** (~80 LOC)
- Migration: ALTER `billing_sessions` ADD COLUMN `game_context TEXT NOT NULL DEFAULT 'unknown'` + `pricing_lock_json TEXT` (snapshots resolved {happy_hour, iracing, applied, locked_rate_paise} at session start)
- Migration: ALTER `wallet_debits` ADD COLUMN `discount_applied TEXT`, `discount_pct REAL`, `game_context TEXT`, `locked_rate_paise INTEGER`
- `POST /billing/start` accepts `game_context: String` in request body; validates against `GameContext` enum (AC, F1_25, iRacing_T2_desktop, AMS2, LMU, rFactor2, Unknown)
- Add `crates/racecontrol/src/pricing/resolve_discount.rs`:
  - `pub fn resolve_discount(now_ist: DateTime, game_ctx: GameContext, customer: &Customer, rules: &PricingRules) -> AppliedDiscount`
  - `AppliedDiscount { discount_kind: enum {None, HappyHour, iRacing}, pct: f64, locked_rate_paise: i64 }`
  - Tier 2 path: iRacing_T2_desktop → 20% if customer.discount_ineligible == false AND happy_hour_pct < 20% (else happy-hour wins per deeper-of)
  - Pure-function unit tests cover 4×3 matrix of {HappyHour ∈ {on/off}} × {GameCtx ∈ {iRacing_T2, AC, Other}} × {discount_ineligible ∈ {true/false}}
- Wallet debit per-tick reads `pricing_lock_json` from session row; stamps debit row with `discount_applied + discount_pct + game_context + locked_rate_paise`

**Phase 2 — Tier 1 iRacing-active gate** (~40 LOC; depends-on RCA-row-1.19 Phase 2)
- `resolve_discount` for `game_context: iRacing_T1` ADDITIONALLY gates on `fleet_iracing_active(state).any_pod()` signal
- If iRacing_T1 game_context BUT no iRacing telemetry present → 20% silently doesn't fire + debit row stamps `discount_applied: None, reason: "iracing_t1_no_telemetry"`
- Test row 1.20 SKIP-reason `IRACING_DISCOUNT_TIER_1_LIVE` flips from always-skip to gated-on-real-fleet-state when iRacing fleet aggregation lands

**Phase 3 — `/api/v1/discount/iracing` introspection endpoint** (~30 LOC; v2.1 incentive page)
- Adds `GET /api/v1/discount/iracing` returning current iRacing-discount state: `{discount_pct, in_window, ineligible_for_customer_X, last_applied_at}`
- Public-facing introspection for PWA "your discount" page (DoD §3 customer-day workflow)
- Read-only; safe for happy-hour-style polling

**Anti-pattern guard:**
- Test asserts `resolve_discount(time, iRacing_T2, customer{discount_ineligible:true}, _) == AppliedDiscount::None`
- Test asserts `resolve_discount(happy_hour_window, iRacing_T2, customer{eligible}, _) == HappyHour 30%` (deeper-of)
- Test asserts `resolve_discount(non_happy_hour, iRacing_T2, customer{eligible}, _) == iRacing 20%`
- Test asserts `resolve_discount(non_happy_hour, AC, customer{eligible}, _) == None` (game-axis correctly differentiates)
- Test asserts NO wallet-debit row exists with `discount_applied IS NULL AND discount_pct IS NOT NULL` (invariant: discount stamp atomic)
