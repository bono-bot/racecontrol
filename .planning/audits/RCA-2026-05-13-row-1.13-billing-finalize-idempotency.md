## 4. V2-alignment delta

V2 `/api/v1/billing/finalize` unified endpoint:

```
POST /api/v1/billing/finalize
Authorization: Bearer <jwt OR service_key>   ← derived from credential, NOT request body
{

→ 200 {

  "finalized_at": "ISO8601",
  "finalize_reason": "...",
```

**Semantic guarantees:**

**§4-A7 — Auth-tier server-side binding-matrix (MMA A7 ABSORBED, 4/5 consensus):**

| `actor` field value | Required credential | Validation rule |
|---|---|---|
| `kiosk` or `staff` | valid staff-JWT in `Authorization: Bearer <jwt>` | JWT.role ∈ {staff, manager, superadmin} |
| `rc-agent` | valid service-key in `Authorization: Bearer <service_key>` | matches `state.config.pods.sentry_service_key` |
| `auto-scheduler` | internal-call source allowlist | caller's IP in `state.config.allowed_internal_callers` OR internal-flag in request context |
| any other / missing | reject | HTTP 401 + `{"error": "actor_credential_mismatch"}` |

**Mismatch handling:** If credential present but doesn't match declared `actor` (e.g. POST finalize with `actor: "staff"` + only service-key) → HTTP 401 + `{"error": "actor_credential_mismatch", "expected_credential_class": "staff-jwt", "received_credential_class": "service-key"}`. Anti-pattern test 9 covers this.

**§4-A2 — Idempotency replay-payload identity validation (MMA A2 ABSORBED, 5/5 consensus):**

UNIQUE constraint scope: `(finalize_idempotency_key)` alone (not composite). On SELECT-by-key match, server compares:
- `payload.session_id` vs stored `session_id`
- `payload.reason` vs stored `finalize_reason`
- `payload.actor` vs stored `finalize_actor`
- `hash(payload.session_id + amount_basis_snapshot)` vs stored `amount_basis_hash`

Three outcomes:
1. **No row:** first call — proceed with finalize transaction
2. **Row matches all 4 fields:** replay — return canonical first response from `billing_session_receipts.idempotency_response_blob` (JSON-serialized) with `idempotency_status: "replayed"`
3. **Row exists but ANY field differs:** payload mismatch — HTTP 409 + `{"error": "idempotency_payload_mismatch", "first_call_summary": {"session_id": "<first>", "reason": "<first>", "actor": "<first>", "finalized_at": "<first>"}}`

This closes the slot 4 gpt-5.4 G-MMA-12 advisory: replay determinism is independent of subsequent session-state mutations because the canonical response is stored at first-call time.

**§4-A3 — Cloud_sync verify timeout/fallback within 1s SLA budget (MMA A3 ABSORBED, 3/5 consensus):**

Finalize handler calls `cloud_sync_verify::verify_push(billing_sessions, session_id)` with hard 200ms timeout budget (well under 1s SLA envelope). Outcomes:

| Verify result | Behavior | Response field |
|---|---|---|
| Succeeds <200ms | Mirror confirmed | `mirror_state: "ok"` |
| Timeout >200ms OR error | Finalize commits LOCALLY; return success | `mirror_state: "pending_async_verify"` |
| Persistent failure (3 retries by reconciler) | Background reconciler marks failed | `mirror_state: "failed"` (on later poll) |

Background reconciler runs at 30s tick, queries `billing_sessions WHERE mirror_state = 'pending_async_verify'`, re-calls `verify_push`. On `failed` persisting >5min: SLA-violation alert fires (wires through Phase 2 alert infrastructure).

Composes-with: §S-242 cloud_sync Phase 1 verify-by-construction (PR #71 MERGED `a22f79b2`). The 200ms timeout-budget contract is NEW doctrine added by this RCA absorption; §S-242 surface defines `verify_push` primitive without prescribing timeout.
