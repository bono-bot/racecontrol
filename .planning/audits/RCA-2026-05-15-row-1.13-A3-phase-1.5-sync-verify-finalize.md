### Q1 — Payload SHAPE: **A (cursor-window) · CONSENSUS 3/3 unanimous**

Use cursor strings derived from the just-written `billing_session.updated_at` value. Payload contains affected tables only (billing_sessions: [<row>], billing_session_receipts: [<row>]). Leverages existing `/sync/echo` contract verbatim — receiver-not-yet-upgraded fail-open works for free.

**Anti-pattern guard (anthropic Risk #1):** `updated_at_minus_1ms` arithmetic is fragile under sub-ms write rates / NTP drift. **Mitigation:** use the actual prior row's `updated_at` from a `RETURNING` clause in the finalize INSERT/UPDATE, NOT arithmetic.

**Anti-pattern guard (nvidia + qwen Risk #2):** sub-millisecond temporal collision when two finalizes within 1ms produce identical cursors. **Mitigation:** RETURNING-clause approach also addresses this (each row has its own `updated_at`).

**Composes-with:** §S-329 fail-open contract · §S-345 soak-in-parallel · existing /sync/echo single-channel doctrine.

### Q2 — Mismatch handling: **α (fail-open) · CONSENSUS 3/3 unanimous**

Treat per-session Mismatch identically to Unavailable: keep `mirror_state="pending_async_verify"` · existing 30s tick picks up async.

**Anti-pattern guard (anthropic Risk #1):** silent persistent-mismatch class — if 30s tick *also* keeps mismatching (e.g., Bono schema drift dropping a column), session stays "pending_async_verify" forever. **Mitigation:** add separate stale-pending metric/alert (NOT a response-field change) — surfacing via verify_outcome enum (Q3-II) is the right channel.

**Anti-pattern guard (anthropic Risk #3 + nvidia Risk #3):** read-replica lag false-positive — receiver querying replica 100ms behind primary will Mismatch on freshly-written row. **Disposition:** expected and tolerable under α (the 30s tick succeeds once replica catches up).

**Composes-with:** A2 idempotency (replay of same idempotency-key must produce identical response regardless of verify outcome path · verify is observability not state).

### Q3 — Audit-trail granularity: **II (always-emit verify_outcome enum) · CONSENSUS 2-1 (qwen → III)**

Emit verify_outcome enum `{"sync_ok", "sync_timeout", "sync_unavailable", "sync_mismatch"}` alongside mirror_state in ALL responses (success and non-OK).

**qwen dissent disposition:** qwen recommended Option III (conditional emit only on non-OK) for response-size optimization. **Anthropic counter-argument adopted:** payload-size argument is negligible (<30 bytes); option III is anti-pattern for typed clients (forces optional-field handling on happy path); option II's `"sync_ok"` positive-signal is useful for SLA dashboards.

**Anti-pattern guard (anthropic Risk #1):** enum-vocabulary lock-in — adding `sync_partial` later requires client-side enum-extension handling. **Mitigation:** document forward-compat — clients MUST treat unknown variant as "pending_async_verify-equivalent".

**Anti-pattern guard (anthropic Risk #2):** redundancy with mirror_state risks divergence (e.g., bug emits mirror_state="verified" + verify_outcome="sync_timeout"). **Mitigation:** server-side invariant assertion before serialization (`debug_assert!(mirror_state == "verified") iff verify_outcome == "sync_ok"`).

**Anti-pattern guard (anthropic Risk #3):** PII/audit-scope creep — verify_outcome will be tempting to extend with `details` payload (mismatch column names, etc.). **Mitigation:** keep enum-only · details go to server-side audit log only.

**Composes-with:** A4 1s SLA tracing (verify_outcome=sync_timeout correlates 1:1 with 200ms-budget span in OTLP) · A6 DPDP cascade (verify_outcome should be part of audit record).

### Q4 — Extension-class auth scope: **Z (middleware + first-consumer pattern) · CONSENSUS 2-1 (qwen → Y)**

Add `Extension(CredentialClass)` injection in `require_staff_jwt` middleware · keep `billing_finalize` as the FIRST consumer · publish migration guide for other handlers · let per-handler migration happen organically.

**qwen dissent disposition:** qwen recommended Option Y (migrate only billing_finalize, no middleware injection yet) for risk-isolation. **Anthropic counter-argument adopted:** Y is the worst option — leaves codebase with two auth-reading patterns in parallel with no forcing-function for convergence (entropy guaranteed). Z establishes the canonical pattern in middleware as forcing-function while limiting blast radius.

**Anti-pattern guard (anthropic Risk #1):** indefinite migration tail — "organic" historically means "never" without tracking issue + deadline. **Mitigation (REQUIRED):** open a tracking issue listing all current `Authorization` header readers in the codebase + set 30-day migration deadline.
