# Phase 445 Wave 0 — ts-rs Spike Report

**Date:** 2026-04-21 05:41 IST
**Question (RESEARCH.md Open Question 1):** Does `ts_rs::TS::export_all_to()` work inside `fn main()` (gen-types binary approach), or must we fall back to `cargo test --features ts-rs export_bindings`?

## TL;DR

**Verdict A — PROCEED with Plan 01 binary approach.** ts-rs 12.0.1 exposes `TS::export(&Config)` and `TS::export_all(&Config)` on the `TS` trait itself, both usable from any function context (not just `#[test]`). The `Config::new().with_out_dir(...)` builder gives the binary explicit control over the output directory. No cargo-test-harness fallback needed.

One API note: **the method is named `export_all`, not `export_all_to`.** Earlier docs (and the RESEARCH.md text) used `export_all_to`; the actual 12.x method signature is `fn export_all(cfg: &Config) -> Result<(), ExportError>`. Plan 01 must use `export_all`.

### Plan 01 implementation sketch (recommended shape)

```rust
// crates/racecontrol/src/bin/gen_types.rs
fn main() -> anyhow::Result<()> {
    let out_dir = PathBuf::from("packages/shared-types/generated/");
    std::fs::create_dir_all(&out_dir)?;

    let cfg = ts_rs::Config::new().with_out_dir(&out_dir);

    // 1. Emit TS bindings (one .ts file per root type per #[ts(export_to = "X.ts")]).
    //    Calling export_all on ANY root type pulls in its transitive TS-derived
    //    dependencies, so we only need to name a handful of "apex" types — the
    //    ones that appear in admin handler return signatures.
    rc_common::types::BillingSessionInfo::export_all(&cfg)?;
    rc_common::types::PodInfo::export_all(&cfg)?;
    rc_common::types::FleetHealthResponse::export_all(&cfg)?;
    // ... one call per apex type from packages/shared-types/generated/.whitelist.txt

    // 2. Emit OpenAPI YAML (utoipa path, orthogonal to ts-rs).
    let openapi = racecontrol::api::openapi::ApiDoc::openapi();
    std::fs::write("docs/openapi.generated.yaml", serde_yaml::to_string(&openapi)?)?;

    Ok(())
}
```

## Plan 01 inputs this spike locks in

1. **Binary strategy**: `fn main()` calling `TS::export_all(&Config)` per apex type. No cargo-test-exec fallback, no `cargo xtask` pattern.
2. **API name**: `export_all`, not `export_all_to` — RESEARCH.md's `export_all_to` reference is outdated; update Plan 01's task actions accordingly.
3. **Config builder**: `Config::new().with_out_dir(&path)` is the canonical way to override `#[ts(export_to = ...)]`'s relative target.
4. **Output format**: each generated `.ts` file opens with `// This file was generated by [ts-rs](https://github.com/Aleph-Alpha/ts-rs). Do not edit this file manually.` — the D-15 drift check includes this preamble as tracked content (no special-casing needed).
5. **`Option<T>` shape**: emitted as `T | null`, not `T | undefined`. Matches Pitfall 2 from RESEARCH.md — admin Zod validators need `.nullable().optional()` for `skip_serializing_if = "Option::is_none"` fields.
