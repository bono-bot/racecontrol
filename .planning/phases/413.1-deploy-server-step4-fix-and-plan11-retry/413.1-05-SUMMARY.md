## Safety guard implementation (revision Issue 4)

Original plan used sed with `${TEST_ROOT//\//\\\\}` parameter substitution that is fragile across shell versions and doesn't reliably preserve backslashes. During initial test run this surfaced as SWAP_CMD_TEST = `del /Q C:RacingPoint-test-413-1750409\...` — missing the leading backslash, would have touched a non-existent path but proved the sed approach is broken.

Replacement approach: **Python3 with `chr(92)`** for literal-backslash substitution. Two transforms in one Python3 heredoc:
1. JSON-decode: `\\` -> `\` (the JSON-string encoding used in the deploy-server.sh `-d '{...}'` arg).
2. Path rewrite: `C:\RacingPoint\` -> `C:\RacingPoint-test-413-<pid>\`.

Pre-run guard then tests the REWRITTEN command for the literal production path via `grep -Fq 'C:\RacingPoint\racecontrol'`. If present, `unsafe_abort` runs and the test exits 2 with the message `UNSAFE: test would touch production paths -- sed rewrite FAILED -- SWAP_CMD_TEST still contains literal C:\RacingPoint\racecontrol`.

On this machine the guard correctly passed (rewrite successful), so abort did not trigger — verified via the OK line `Layer 2 pre-run safety guard: test paths rewritten to sandbox (no production leakage)`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 — blocking issue] sed path-rewrite in the plan's recommended code was broken**

- **Found during:** First test run after Write
- **Issue:** The plan's recommended sed expression `s|C:\\\\RacingPoint\\\\|${TEST_ROOT_WIN}\\\\|g` with `TEST_ROOT_WIN="C:\\RacingPoint-test-413-$$"` produced `C:RacingPoint-test-413-<pid>\` (missing leading backslash) because bash double-quoted `\\` expands to `\` and sed's replacement interprets the resulting `\R` as an escape sequence, consuming the backslash.
- **Fix:** Replaced sed with Python3 heredoc using `chr(92)` + `str.replace`. Unambiguous, no shell escape layers. The plan's pre-run safety guard language (`UNSAFE: test would touch production`) is preserved verbatim.
- **Verification:** Re-ran test — Scenario A now shows SWAPPED and correct file swap; DEBUG line shows `C:\RacingPoint-test-413-<pid>\racecontrol.exe` (full Windows path with leading backslash).
- **Commit:** Part of `955b625b`.

**2. [Rule 2 — missing critical functionality] Scenario A/B output-matching needed CR trimming**

- **Found during:** Scenario A initially failed with `expected NEW-BINARY, got: NEW-BINARY` (identical-looking strings).
- **Issue:** cmd.exe writes files with CRLF line endings on Windows; `echo NEW-BINARY > file` then `cat file` returns `NEW-BINARY\r\n`. Direct string comparison against `"NEW-BINARY"` fails due to trailing `\r`.
- **Fix:** Added `tr -d '\r\n'` trim to the file-content read before comparison. Both Scenarios A and B and Layer 3 now use the trimmed form.
- **Files modified:** tests/deploy_script_swap_test.sh
- **Commit:** Part of `955b625b`.

## Scenarios dropped (Revision Issue 10)

Scenario C: barrier-based auto-recover. Barrier timing (`sleep 0.2 && echo BARRIER > racecontrol.exe &` in background vs. `cmd.exe //c "$SWAP_CMD_TEST"` in foreground) did not reliably create a race window on this runner. cmd.exe on Windows executes the 1st and 2nd ren back-to-back in < 200ms, so the barrier typically lands AFTER the 2nd ren already succeeded, making Scenario C fall through to the happy-path result (SWAPPED).

Per revision Issue 10: Scenario C is **explicitly DROPPED** when the barrier doesn't trigger a failure. Not treated as test failure. The compensating controls are:
1. Layer 1's `SWAP_FAILED_RECOVERED` >= 1 grep (static proof the code path exists).
2. Plan 06's live canary (production-grade proof it fires correctly).

The DROP message is printed on stdout with full rationale, so the audit trail is preserved for any CI log reviewer.
