# What to search for

## Primary pattern sources (where manual-state provisioning usually lives)
1. `setx /M` calls in .bat and .ps1 files under scripts/
2. `reg add HKLM\...` calls in deploy scripts
3. `$env:<VAR>` reads in PowerShell scripts (infer: whoever writes it is the provisioner)
4. `std::env::var(...)` calls in Rust code on pods — any env var ending in `_KEY`, `_SECRET`, `_TOKEN`, or related to identity/auth
5. `process.env.<VAR>` in Node.js files in scripts/
6. Documentation references to "set X on each pod" or "manually provision" under docs/

## Where to look
- `scripts/` (all subdirs)
- `docs/` (all files)
- `crates/rc-agent/src/` and `crates/rc-sentry/src/`
- D:\pod-deploy\ (pendrive kit, if readable from James — probably not from bash, but docs for it may be in scripts/deploy/)

## Known categories

- **Migrated by this phase**: `RCAGENT_SERVICE_KEY` (Plans 01-04 replace HKLM reg with server fetch)
- **Intentionally user-managed (keep as-is)**: `SENTRY_KEY` (rc-sentry uses its own key, set by the deploy operator; CONTEXT.md explicitly out of scope); `OPENROUTER_KEY` (MMA-only, James .27 managed); `COMMS_PSK` (comms-link; separate system)
- **Candidate for future migration**: any LAN-specific config (server IP, pod ID) that's set via HKLM reg; any pod-specific TOML fragments. These should be listed in PROVISIONING-AUDIT.md as TO-MIGRATE with a brief argument for why a boot-fetch pattern could replace them.
