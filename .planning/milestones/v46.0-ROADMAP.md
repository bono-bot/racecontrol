## Phase Details

### Phase 361: Kiosk Preset Filtering + Server Gate

**Goal:** Every kiosk staff-wizard session gets filtered to valid car/track combos for the chosen pod, and invalid combinations cannot reach the game launcher.

**Requirements:** GLD-A-01..04

**Success criteria:**
1. Kiosk car/track dropdowns hide entries not installed on the selected pod (checked against `/api/v1/pods/{id}/inventory` response from a live pod).
2. Invalid combos disable "Start Session" with an inline reason message that references the failing `presetValidity` rule.
3. Server `/sessions/start` returns HTTP 422 + `{reason, suggestion}` body when a client bypasses the kiosk filter (verified via direct `curl` test with a known-bad combo).
4. Admin `/admin/content-drift` lists any pod whose physical inventory no longer matches the TOML expectation.

**Plans (to be generated by gsd-planner):**
- [ ] 361-01-PLAN — Server: `/api/v1/pods/{id}/inventory` endpoint + server-side validity gate
- [ ] 361-02-PLAN — Kiosk: filter dropdowns + wire `presetValidity` surface
- [ ] 361-03-PLAN — Admin: `/admin/content-drift` page + nyquist tests

**Subagent gates:** `gsd-ui-researcher` → `gsd-ui-auditor` (kiosk + admin UI), `gsd-nyquist-auditor` (validity gate logic).

### Phase 363: Data Recording Verification

**Goal:** Every completed session has a lap audit, a telemetry completeness score, an auto-synced CSV fallback path, and a 5s billing grace window so lap-rejects can't cause billing races.

**Requirements:** GLD-C-01..04

**Success criteria:**
1. Lap audit runs at session end and marks sessions with >10% lap-count gap as `incomplete`.
2. Telemetry completeness score is persisted to `sessions.telemetry_coverage_pct` and sessions <80% are marked `suspect: true`.
3. CSV fallback syncs within 30s of session end (verified by killing primary ingest mid-session and checking sync timestamp on server).
4. Billing finalize delayed 5s after session end; lap-reject arriving in that window updates refund calc before it commits (verified by synthetic test with forced lap-reject).

**Plans:**
- [ ] 363-01-PLAN — Lap audit + telemetry completeness scorer + DB migration for `telemetry_coverage_pct` + `suspect`
- [ ] 363-02-PLAN — CSV fallback auto-sync path
- [ ] 363-03-PLAN — Billing 5s grace window + lap-reject race fix

**Subagent gates:** `gsd-nyquist-auditor` (billing race = financial flow), MMA audit mandatory (billing + data bridge).

### Phase 364: Session Quality Monitor

**Goal:** In-flight telemetry quality issues are detected and logged/alerted BEFORE session end, not discovered post-hoc.

**Requirements:** GLD-D-01..05

**Success criteria:**
1. `TelemetryGap` events fire for >500ms gaps and are routed to the `session_quality` log category (not silently dropped).
2. Lap consistency checker flags >3σ outliers with `suspect_reason: "lap_time_outlier"`.
3. Stalled session detector fires `SessionStalled` warning after 15s of in-race telemetry silence.
4. Zero `let _ = ws_send(...)` patterns remain in the session/telemetry hot path (verified by `rg "let _ = .*ws_send" crates/`).
5. `try_send` buffer overflow counter exposed at `/metrics` as `ws_try_send_overflows_total`.

**Plans:**
- [ ] 364-01-PLAN — Telemetry gap / stall detectors + WS event wiring
- [ ] 364-02-PLAN — Lap consistency checker (rolling σ)
- [ ] 364-03-PLAN — Silent-drop audit: replace all `let _ = ws_send` + buffer overflow metrics

**Subagent gates:** `gsd-nyquist-auditor`, MMA audit.

### Phase 365: AI Behavior Validation via MMA

**Goal:** Build a knowledge base of expected AI lap times per (car, track, difficulty_tier) and alert when live AI behavior deviates from the KB.

**Requirements:** GLD-E-01..04

**Success criteria:**
1. `ai_behavior_samples` DB table populated by >0 rows after any AI session lasting >3 laps (verified via live launch on Pod 8).
2. Weekly MMA batch job produces KB updates in `.planning/kb/ai-behavior/` with signed consensus (3/5 models agree).
3. `AiBehaviorAnomaly` WS event fires when live AI median lap time falls outside KB band for >3 consecutive laps.
4. Admin dashboard surfaces per-car-track AI performance trend (shared UI with Phase 367).

**Plans:**
- [ ] 365-01-PLAN — `ai_behavior_samples` schema + collector hooks into existing lap ingest
- [ ] 365-02-PLAN — Weekly MMA batch job + KB file format
- [ ] 365-03-PLAN — Live anomaly detector + WS event

**Subagent gates:** `gsd-nyquist-auditor`, MMA audit (cross-system data bridge + AI judgment).

### Phase 366: Fleet Intelligence

**Goal:** Per-pod health becomes a rolling composite signal, not a binary "up/down." Content drift and concurrent sessions are prevented at the server.

**Requirements:** GLD-F-01..04

**Success criteria:**
1. `/fleet/intelligence` endpoint returns a 0-100 composite score per pod with component breakdown.
2. Time-of-day anomaly report identifies pods with hour-correlated failure rates (verified by seeding known failure pattern into test data).
3. Content-drift detector fires `ContentDriftDetected` event when a pod's installed inventory diverges from expected TOML by any delta.
4. Attempting to start a second session on an already-active pod returns HTTP 409 with the active session ID (verified by parallel `curl` smoke test).

**Plans:**
- [ ] 366-01-PLAN — Per-pod health score aggregator + `/fleet/intelligence` endpoint
- [ ] 366-02-PLAN — Time-of-day pattern analysis
- [ ] 366-03-PLAN — Content drift detector (reuses GLD-A-04 groundwork)
- [ ] 366-04-PLAN — Concurrent session guard (server-side mutex on `(pod_id, state=Active)`)

**Subagent gates:** `gsd-ui-researcher` → `gsd-ui-auditor` (admin `/fleet/intelligence` page), MMA audit (fleet-wide impact).
