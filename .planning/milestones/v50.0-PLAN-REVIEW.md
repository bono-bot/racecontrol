### Phase 430 — Accessibility Service Foundation — VERDICT: FLAG

**Top 3 risks / gaps**

1. **`serviceScope` referenced inside `GestureDispatcher` but never plumbed in.** 430-03 uses `serviceScope.launch { delay(1000)... }` for gesture timeout, but `GestureDispatcher` only takes `bridge: A11yBridge` in its constructor. The canonical scope lives on `AgentForegroundService`. Compile error or silent fallback to `GlobalScope` (leaks on service death) likely. Same bug repeats in `/ui/swipe` timeout.
2. **Concurrent-caller race on `A11yBridge.tryGetService() → performAction`.** `AccessibilityNodeInfo` handles returned to handler A can be recycled by handler B's `resolve()` cleanup path, because no mutex/queue serialises UI-action requests. Two parallel `POST /ui/tap` calls (or `/ui/tap` + `/screen/tree`) can hit `IllegalStateException: Cannot perform this action on a sealed instance.` and return 500 intermittently — breaks the 95% SC-2 threshold non-deterministically.
3. **MainActivity early-exit pattern races the Foreground Service.** `startForegroundService(...) ; if (!enabled) startActivity(setup) ; finish()` in step 5 of 430-06 can finish MainActivity before Android binds the foreground service on Android 14 (stricter FGS launch timing), and the setup Activity may launch before A11yStateMonitor begins polling — "Unknown → Enabled" transition in the first 10 s will NOT auto-dismiss because `onCreate` creates a second monitor instance with its own poll cycle.

**Top 3 strengths**

1. Must-haves (§3 T-1..T-10) are genuinely user-observable (`curl ... returns JSON`, notification text flips, Toast appears) and each maps cleanly to a specific task.
2. R-8 (silent service crash) correctly modelled as two-source-of-truth (`ENABLED_ACCESSIBILITY_SERVICES` ∩ `A11yBridge.isConnected()`), catches failure mode Android hides from users.
3. Node recycling hygiene explicit in ScreenTreeReader AND SelectorResolver AND at handler level; R-9 documents `adb shell dumpsys accessibility` runtime audit.

**Execution-blocking items NOT surfaced as OQs**

- **OQ-missing-A:** `AccessibilityService.onUnbind` fires on DISABLE-by-user; `onDestroy` fires on service kill. Which is authoritative "bridge unregister" signal? OneUI calls `onUnbind` twice.
- **OQ-missing-B:** Android 14 (API 34) added `accessibilityDataSensitive="accessibilityDataPrivateYes"` default for sideloaded APKs — Zomato Partner may set this, blocking tree read.
- **OQ-missing-C:** `findAccessibilityNodeInfosByViewId` requires un-obfuscated resource IDs. Zomato Partner is a minified release build with likely stripped ids. No fallback strategy OQ — resource-id selectors may fail fleet-wide on the very apps this phase exists to automate.

### Phase 432 — Driver Framework + Capability Registry — VERDICT: FLAG

**Top 3 risks / gaps**

1. **Capability-split enforcement is not enforced — it's only self-reported.** Nothing prevents two devices from claiming the same `driver_id` simultaneously. `supported_device_types` filters *device→driver*, not *driver→singleton across fleet*. When Zomato runs on Tab Plus and M07 both accept it (both in `["tablet","phone"]`), both will install, both will humanize-tap, both will double-accept orders. Server-side arbitration missing from `CapabilityRegistry`. This is the "cafe-front race condition" class.
2. **Reflection + ProGuard is a runtime-only failure mode with no pre-ship gate.** R-9 mentions `-keep class ...sample.**` but future drivers (Zomato at `in.racingpoint.drivers.zomato.ZomatoDriver`) sit outside `sample.**`. Keep rule pattern stales on first real driver. No CI step asserts "every `driver_class` in every bundled manifest resolves via `Class.forName` on a release (minified) build."
3. **Lifecycle race: PackageMonitor dynamic registration vs `installAllEnabled()`.** `AgentForegroundService.onCreate` sequence calls `installAllEnabled()` BEFORE `registerReceiver(PackageMonitor)`. A `PACKAGE_REPLACED` that fires during the install window is lost. Also: `installAllEnabled()` uses `enabled_by_default` only; no persisted state of "user toggled this off last session" — after reboot, every `enabled_by_default:true` driver re-installs regardless of prior uninstall.

**Top 3 strengths**

1. Interface-first sequencing (432-01 lands contracts before any implementation) combined with mid-phase MMA audit gate between 432-02 and 432-03 is correct — calcification risk actively managed.
2. `SupervisorJob + CoroutineExceptionHandler + CoroutineName` isolation pattern is textbook-correct Kotlin idiom; 432-08 tests with PID-before/PID-after on real device.
3. `capabilities_digest` (SHA256) on every heartbeat with forward-compat `ignoreUnknownKeys=true` is cheap, correct change-detection aligned with PROTOCOL.md v1 envelope.

**Execution-blocking items NOT surfaced as OQs**

- **OQ-9 (missing):** Fleet-level capability uniqueness. Who owns "Zomato" when Tab Plus and M07 both claim it? Server arbitration, first-claim-wins, explicit multi-device, or manual assignment.
- **OQ-10 (missing):** Persisted enable state across reboot. Staff-toggled-off driver silently re-enables on every reboot/OTA.
- **OQ-11 (missing):** Remote APK swap vs driver hot-reload. v50.0 OTA boundary undefined.

## Wave 2 — Platform Phases (433–436)

### Phase 433 — Selector DSL + Hot-Reload — VERDICT: FLAG

**Top 3 risks / gaps**

1. **App-version *detection* is pull-based, not event-driven.** Resolver calls `PackageManager.getPackageInfo().versionName` at each `resolve()`. When Zomato auto-updates v3.14.2→v3.15.0 mid-session, no `ACTION_PACKAGE_REPLACED` BroadcastReceiver — only passive detection on next driver action, races a cached selector hit. `onAppUpdate(old,new)` hook is *defined* but nothing in 433-04 *fires* it. Tab Plus could spend hours on stale v-current.
2. **Replay protection is per-(app,version) but `.patch_version` file is trust-on-first-use.** `supersedes_patch_version >= current` — if `.patch_version` is missing/deleted (e.g. on adb `rm -rf filesDir/selectors` rollback path), attacker who captured envelope `patch_version=2` can replay it post-reset. No anti-rollback floor in BuildConfig or signed alongside.
3. **Canonicalization scheme is textual, not YAML-semantic.** Signing raw LF-normalized YAML bytes — any proxy, git client, or editor that re-indents or re-quotes invalidates signature silently. JCS-style or SHA-over-parsed-AST would be sturdier. Also: SnakeYAML-Engine `setAllowDuplicateKeys(false)` is set, but depth/alias/anchor bombs (billion-laughs class) aren't capped.

**Top 3 strengths**

1. Hot-reload concurrency model is genuinely sound — `AtomicReference<SelectorMap>` + per-action snapshot + 300ms FileObserver debounce cleanly solves mid-action swap races. R-2 plans One UI FileObserver fallback via 60s mtime reconciliation.
2. Dedup key `driver:screen:element:appVersion` correctly includes app_version, so v3.15.0's fresh breakage isn't suppressed by v3.14.2's 60s window.
3. Phase 443 integration surface clean: envelope shape + canonicalization rule + trusted key-ID list documented in `comms-link/shared/agent-protocol-v1.md` and `docs/SELECTORS.md §Signing`.

**Execution-blocking OQs missing**

- App-update detection mechanism (passive pull vs `PACKAGE_REPLACED` receiver vs `versionCode`-cached-in-catalog).
- `.patch_version` persistence + anti-rollback floor after selectors-dir wipe (rollback doc and replay protection contradict).
- YAML-bomb / resource-exhaustion limits in SelectorParser (max depth, max aliases, max doc size).

### Phase 435 — Humanize Layer + Audit Log — VERDICT: FLAG (ToS-core gaps)

**Top 3 risks / gaps**

1. **Gaussian timing is a BOT SIGNATURE, not humanization.** DelayInterceptor uses `Random.nextGaussian()` on PER-ACTION profile (TAP: 800±200). Real human inter-action timing on mobile apps follows **log-normal** (heavy right tail — occasional long pauses to read/think), NOT Gaussian. Clamping at 0 with `coerceAtLeast(0L)` creates non-zero density floor that bot-detectors flag. Zomato's internal timing models (and any off-the-shelf detection SDK like Arkose/DataDome) fingerprint Gaussian-with-zero-clamp as automation within ~100 samples. Plan hardcodes `nextGaussian()` AND tests `DelayDistributionIsGaussian` as PASS — test verifies the wrong distribution.
2. **No session-level shape, no inter-app think-time, no circadian modulation.** Rate limit is token-bucket at 1-minute granularity per `(driver_id, app_package)`. Real drivers have: burst-then-pause session envelopes (3–8 actions in 10s, then 30–120s read), inter-app transition costs (500ms–3s), time-of-day load curves. BusinessHoursGate is hard 08:00–23:00 step function — a bot-like square wave. Detectable in aggregate within 24h of telemetry.
3. **Shipping-stall + 500MB cap = silent ToS-evidence loss, and the stub hides it.** OQ-4 chose "drop oldest" on 24h+ shipping stall. Combined with 435-08 being a stub that returns 200 without storing, plan ships with **zero durable audit evidence anywhere**. If ToS dispute lands during v50.0 window (before Phase 441), there is no audit trail server-side. Stub's success 200 also causes `ShippedCursor` to advance and agent to delete shipped-but-discarded events on rotation.

**Top 3 strengths**

1. No-lock-across-await enforced structurally (RateLimiter Mutex released before `chain.proceed()`, `kotlinx-coroutines-debug` instrumentation in Test 6) — prevents bug class flagged in v27.0 MMA.
2. ReentrantReadWriteLock + rename-aware cursor callback correctly handles mid-read rotation race.
3. FLAG_SECURE / API<30 / timeout / error sentinels are distinct (`sha256:unavailable:<reason>`) — preserves audit completeness when visual evidence unavailable.

**Execution-blocking OQs missing**

- **Distribution family choice (Gaussian vs log-normal vs empirically-sampled).** Single biggest ToS-detection lever in the whole phase; planner made it unilaterally inside 435-01. Switching post-435-09 invalidates the drill.
- **Screenshot hash PII risk for TextInput flows is only partially addressed.** OQ-3 covers redact on `TextInput.text`, but PNG screenshot captured after TextInput dispatch contains rendered text (typed OTPs, phone numbers, order notes). No OQ on "should ScreenshotCapture skip entirely when `action_type==TEXT_INPUT && redact=true`?"
- Endpoint path mismatch: user said `/mobile/audit/ingest`, plan uses `/api/v1/mobile-audit/ingest`.
- Queue-until-window survives agent restart = NO (R-8 acknowledges, §9 doesn't ask; missed Zomato order = real money lost).
- Stub→real cutover atomicity — if Phase 441 returns 200 before durable commit and crashes mid-flight, events advance cursor AND get lost.

**Top 3 risks / gaps**

No runtime SLO monitor for "devices that haven't ACKed a kill-switch within 10s."

2. Pre-register buffer replay queue (Risk 7) — rare to see this anticipated pre-execution.
3. Re-uses v22.0 `feature_flags` table + mirrors `crates/rc-agent/src/feature_flags.rs` — genuinely additive, not parallel system.

**Execution-blocking OQs missing**

- Kill-switch actor authorization scope — ANY staff role, or manager+? ToS incident response at 2am by junior staff is a policy question.

## Wave 3 — Driver Phases (437–440)

### Phase 437 — Zomato Partner Driver — VERDICT: FLAG (HIGHEST ToS RISK)

**Top 3 risks / gaps**

1. **No order-lifecycle coverage beyond accept→mark-ready.** Real Zomato flow includes: customer refund/cancellation mid-prep, stockout after accept, customer edits, delivery-partner assignment/rejection, rider-arrived, order-picked-up. Plan only models accept/reject/mark-ready. Selectors capture 5 screens (order_list, order_detail incoming, order_detail accepted, login, main dashboard) — real Zomato Partner has ~12-15 order states. **Selector coverage estimate: ~40%.** First real refund or stockout notification hits SelectorMiss, throws, leaves UI in undefined state with no recovery plan. R-6 dismisses cancellation as "Zomato handles it" — wrong, because Partner app typically requires staff to ACK cancellation, which the bot now blocks.
2. **Capacity-gate race: TOCTOU between query and tap.** `query()` at T=0, grace 20s, re-query, accept at T+22s — queue_depth can cross max during that window (a walk-in cafe order lands via POS). Plan auto-accepts against stale snapshot. No reservation/decrement on query, no CAS on accept. Also: `can_accept=true` from server is not durable — if Tab Plus's HumanizeInterceptor delays tap 8s, another driver (future HyperPure on M07) may consume capacity. No cross-driver capacity lock.
3. **Audit trail insufficient for account-ban post-mortem.** `screenshotHash` logged but SCREENSHOT itself isn't retained (hash alone can't prove to Zomato ops we weren't botting). No outbound Zomato push-notification log (inbound only). No wall-clock + monotonic-clock pair (humanize variance can be spoofed if clock drifts). No recording of which selector-version matched which tap. Phase 435 audit log format isn't specified to survive the 7-day post-ban forensic window.

**Top 3 strengths**

1. Dual-mode MMA + Uday checkpoint gating at 437-11 correctly structured and blocks 437-12.
2. Fail-closed on capacity errors + killswitch-allows-inflight-completion is right ToS posture.
3. PII masking + DPDP consideration in ForwardClient (437-08) is a rare correct proactive touch.

**Execution-blocking OQs missing**

- Zomato push-notification interaction — agent opens app on notification; Zomato's own in-app banner for NEXT order can intercept tap mid-sequence.
- What screen-state does driver leave UI in after crash mid-tap? No "resume/recovery" selector.
- Screenshot retention policy + legal-hold for ban post-mortem. Must be in CONTEXT, not deferred.
- Test account = live account conflict. OQ-2 falls back to production account with "5 small real orders" — that IS the ToS violation the phase is trying to prevent. Needs Uday decision BEFORE 437-01, not at drill time.

Recommended planner revisions: (1) stockout/refund/cancellation selector coverage in 437-01, (2) capacity-reservation pattern in 437-05/06, (3) screenshot retention + raw-log spec in 437-11 prep, (4) promote missing OQs to blockers answered before 437-01.

### Phase 438 — HyperPure Driver — VERDICT: FLAG

**Top 3 risks / gaps**

1. **No idempotency key on `/api/v1/inventory/order-placed`.** Handler updates by `manifest_id` alone. If agent POSTs success, network drops before 200, agent retries (standard OkHttp behaviour), handler re-updates row, re-broadcasts `OrderPlacedEvent`, re-fires WhatsApp "Order confirmed" message. R-10 (silent-success) guarded, but symmetric risk (staff seeing same confirmation twice) is not. No `IF status IN ('dispatched','placed_unverified') THEN UPDATE` guard; no receipt-hash dedupe. Combined with Core-side duplicate-trigger risk (multiple `cafe_stock` event-storm paths → `enqueue_depletion` called twice, debounce is per-call), **end-to-end path is not exactly-once in either direction**.
2. **"Order placed on HyperPure" ≠ "delivery received at venue" is unaddressed.** Success criteria stop at confirmation capture. No reconciliation that a HyperPure order with `delivery_window_end` in the past was actually received — no webhook consumption, no staff "mark received" flow, no auto-flag for missed deliveries, no reverse adjustment to `cafe_stock`. R-14 and OQ-8 defer to Phase 13. Goal statement ("closes the inventory loop Core → HyperPure → Core") is therefore NOT closed by this phase — only Core → HyperPure → order-placed-ACK is closed.
3. **Inventory-depletion trigger spec has three undefined edges.** (a) `enqueue_depletion` called from `check_low_stock_alerts` AFTER WhatsApp alert — periodic tick means same item enqueues on every tick until replenished (5-min debounce coalesces one burst but second 5-min tick issues SECOND manifest for same SKU). (b) No "order-in-flight" suppression: if `hyperpure_orders` has row with `status IN ('dispatched','placed')` for `cafe_item_id=X`, depletion for X must not enqueue again until order received or aged out. (c) Partial substitution: plan doesn't capture auto-substitution at checkout; no `substituted_skus` in `OrderPlacedReceipt`.

### Phase 443 — Selector Map Remote-Push UI — VERDICT: FLAG (security-critical)

**Top 3 risks / gaps**

1. **Signing oracle is a shared admin JWT — no 4-eyes, no per-push approval, no rate limit.** Plan requires "admin role" via existing `require_admin`/`StaffAuth`. In v47.0 admin hardening context, admin JWT is reused by multiple staff. ANYONE with admin JWT (or stolen one) can sign+push a patch that taps "Accept all free orders" on HyperPure. 2. **Rollback UX fails 2am test for the "bad patch that breaks the admin dashboard" case.** Rollback is server-authoritative + re-signs previous YAML as N+1 — good. BUT: if bad patch crashes device or device goes offline before applying, rollback re-ships via comms-link which requires device online. No plan mandates: (a) kill-switch envelope that disables selectors entirely (agent falls back to stock UI), (b) admin-side "freeze pushes" global lock, (c) recovery when BOTH Tab Plus + M07 accept a bad patch simultaneously. Plan says "push manual rollback via adb" but adb at 2am on reception tablet is not 2-minute recoverable.
3. **Ed25519 canonicalization documented in prose, not pinned by shared golden-vector test.** Plan 443-03 verifies server canonicalization independently; Phase 433 verifies agent canonicalization independently. NO cross-repo test signs on server and verifies with agent's actual `PatchSignatureVerifier` byte-for-byte. Needs committed test-vector YAML + expected signature hex as cross-crate fixture.

**Top 3 strengths**

1. Server-authoritative rollback is the correct architectural choice — no new agent code, `patch_version` monotonicity via DB UNIQUE, re-push reuses all audit infrastructure. Replay protection via `UNIQUE (app_package, app_version, patch_version)` enforced at DB layer.
2. Audit trail complete by construction — `actor_staff_id` + `actor_jwt_hash` + `yaml_sha256` + per-device status + history endpoint. Satisfies non-repudiation; typed-confirmation + SecurityWarningBanner actively discourage accidents.
3. security-check.js assertions added PRE + POST; SEC-GATE-01 is deploy gate; private-key-never-touches-browser invariant (T-10) has concrete test. `.gitignore` hardening for `*-ed25519.pem` + pre-commit hook catches PEM leaks at commit time. Key storage explicitly presented to Uday as `checkpoint:decision`.

**Execution-blocking OQs missing**

## Cross-Phase Themes (patterns that repeat across multiple PLANs)

1. **Schema contracts handshaked in prose, not in cross-phase contract tests.** 441 declares `MobileAuditRow` NOT NULL fields that 435's stub doesn't emit. 443's canonicalization rule is documented separately on server (Rust) and agent (Kotlin) sides — no shared golden-vector fixture. 434 references a Bono VPS `/alerts/session-expired` endpoint that doesn't exist. Every cross-phase interface needs a committed contract test (YAML fixture + expected bytes/hex) BEFORE consumer and producer both ship.

2. **Stub phases advance cursors on 200 OK when the payload was discarded.** 435-08 stub returns 200 without durable storage; agent's `ShippedCursor` advances; events gone. Same failure mode for 443-06 retry endpoint (no auth + re-signs silently) and 438-04 order-placed handler (double-POST = double-WhatsApp). **Rule**: cursor-advance semantics should be "server returned `durable:true`", not "server returned 200."

3. **Offline / partitioned boundary is undefined across 3 phases.** 436: no max-offline-then-halt timer (cached `enable_zomato=true` runs indefinitely after Tailscale drop). 442: no UI fallback when PUT `/flags` times out (2am = server is sick). 444: no OS-update guard (one Android update can disable Accessibility service fleet-wide overnight). Network-partition failure modes need a milestone-wide policy.

4. **In-flight ToS-action cancellation is inconsistent.** 436 kill-switch does `scope.cancel()` without a best-effort "reject/cancel" upstream to Zomato. 437 reads the kill flag between actions but doesn't define state after a mid-action scope-cancel. 444 drill 4 tests kill-switch latency but not "what did the Zomato account see on their side." A kill-switch that leaves a half-accepted order IS the ToS incident it's supposed to prevent.

5. **Humanize distribution is a bot signature by default.** 435 ships Gaussian timing with zero-clamp + hard 08:00–23:00 square-wave business-hours gate. Detectable in aggregate within 24h of telemetry by any off-the-shelf detection SDK (Arkose/DataDome/Zomato-internal). Needs log-normal per-action distribution + session envelope + inter-app think-time + circadian modulation BEFORE 437 live-drill, not after.

6. **Selector coverage is partial.** 437 maps ~40% of Zomato Partner screens (no refund/cancellation/stockout/edits/rider-assignment). 438 has no substitution-at-checkout capture. 439 aborts on OOS instead of substituting. First real edge case → SelectorMiss → UI in undefined state. Goal-backward: "fully automate Zomato" is not what any of these plans deliver today.

7. **Security oracles are over-scoped to "admin JWT".** 443 signing endpoint accepts any admin JWT (no 4-eyes, no re-auth, no rate limit). 442 kill-switch accepts any admin JWT at 2am. Both need scoped-auth (`mobile.selectors.sign`, `mobile.kill_switch`) and re-auth/2FA. v47.0 admin hardening context makes this more urgent — admin JWTs are reused by multiple staff.

8. **Goal statement vs delivered capability mismatch.** 429 SC-1 says "devices visible in `/fleet/health`" but `/fleet/health` is pods-only — plan retargets to `/relay/health`. 438 goal says "closes the inventory loop Core → HyperPure → Core" but delivery reconciliation is deferred to Phase 13. 444 says "E2E drills" but drills don't cover shadow-ban / SDK update / OS update. **Rule**: SC must be verifiable by artifacts this phase ships.

9. **Human-in-the-loop is assumed, not trained.** 442 + 443 + 444 assume trained reception staff can operate kill-switches + runbooks at 2am. No phase in 429–443 produces staff training. Memory suggests this goes to a post-v50 phase — but kill-switches that nobody can operate are theater.

10. **Infrastructure pre-reqs are referenced, not built.** 434 WhatsApp alert endpoint on Bono VPS (OQ-1) — doesn't exist. 443 Ed25519 signing key storage (OQ 443-02) — no decision. 437 Zomato test account — plan falls back to production with 5 small real orders, which IS the ToS violation the phase is trying to prevent. These are Uday-tier blockers masquerading as planner OQs.
