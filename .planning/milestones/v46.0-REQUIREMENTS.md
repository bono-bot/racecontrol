**Defined:** 2026-04-09 (retroactive — Phase 362 Layer 3 already shipped as build `a9b5eaa3` on all 8 pods)

### Phase 361 — Kiosk Preset Filtering + Server Gate (Phase A)

**Goal:** Prevent invalid car/track combos at the source. Wire up the unused `presetValidity` signal, filter kiosk selections by pod inventory, and reject invalid combos at the API boundary.

- [x] **GLD-A-01**: Kiosk staff wizard reads each pod's game/car/track inventory from `/api/v1/pods/{id}/inventory` and filters the car/track dropdowns to only what that pod has installed. *(361-01 DEPLOYED 2026-04-11)*
- [ ] **GLD-A-02**: Kiosk staff wizard surfaces the previously-computed `presetValidity` value in the UI — invalid combinations disable "Start Session" with an inline reason.
- [x] **GLD-A-03**: Server `/api/v1/sessions/start` rejects any session request whose `(pod_id, game, car, track, ai_count)` tuple fails a server-side validity check, returning HTTP 422 with a structured `{reason, suggestion}` body. *(361-01 DEPLOYED 2026-04-11 — gate in launch_game, backward-compat 200 wrapper with body.status=422)*
- [x] **GLD-A-04**: Admin `/admin/content-drift` page lists pods whose physical inventory no longer matches the expected pod TOML (ACR-02 hardening for Phase 366 consumption). *(361-03 code-complete 2026-04-11 — /fleet/content-drift with functional drift detection, deploy pending)*

**Closes silent-loss points:** P0-02 (`presetValidity` unused in kiosk), P2-08 (no server-side combo rejection).

### Phase 364 — Session Quality Monitor (Phase D)

**Goal:** Detect in-flight session quality degradation before the customer finishes, so staff can intervene or the system can mark the session for review.

- [ ] **GLD-D-01**: Telemetry gap detector — any gap >500ms in the telemetry stream fires a `TelemetryGap` event (today the event exists but is `let _ =`'d).
- [ ] **GLD-D-02**: Lap time consistency checker — flags laps that are >3σ from the driver's rolling session mean as suspect.
- [ ] **GLD-D-03**: Stalled session detection — sessions with no telemetry for >15s while `game_state == InRace` fire a `SessionStalled` warning.
- [ ] **GLD-D-04**: Fix all `let _ = ws_send(...)` silent drops in the hot path — replace with `if let Err(e) = ... { tracing::warn!(...); metrics::inc("ws_send_drops"); }`.
- [ ] **GLD-D-05**: Wire `try_send` buffer-overflow counter into `/metrics` so overflow is observable.

**Closes silent-loss points:** P1-01 (WS `let _ =` silent drops), P1-02 (`try_send` buffer overflow), P1-04 (`TelemetryGap` ignored), P2-03 (10Hz cap — surfaces here).

### Phase 365 — AI Behavior Validation via MMA (Phase E)

**Goal:** Confirm AI opponents behave appropriately for their assigned difficulty tier. Build a knowledge base of expected AI lap times per car/track/difficulty.

- [ ] **GLD-E-01**: AI lap time collector — after lap 3 of any AI session, median AI lap times are recorded to `ai_behavior_samples` table keyed by `(car, track, ai_level, ai_aggression)`.
- [ ] **GLD-E-02**: MMA difficulty-tier comparison — weekly batch job runs MMA on collected samples to detect tier misalignment (e.g., "Pro" AI running slower than "Semi-Pro" expected band).
- [ ] **GLD-E-03**: AI behavior KB in `.planning/kb/ai-behavior/{car}-{track}.toml` — expected lap time band per difficulty tier, updated from MMA consensus findings.
- [ ] **GLD-E-04**: Anomaly alerts — live sessions whose AI lap times fall outside the KB band fire `AiBehaviorAnomaly` WS event.

**Closes silent-loss points:** P2-07 (no AI behavior validation), P2-11 (difficulty tier contract untested).

### Phase 366 — Fleet Intelligence (Phase F)

**Goal:** Aggregate per-session signals into per-pod intelligence. Detect fleet-level drift and prevent concurrent session bugs.

- [ ] **GLD-F-01**: Per-pod health score — rolling 7-day composite of: session success rate, telemetry completeness, config mismatch rate, crash rate. Surfaced in admin `/fleet/intelligence`.
- [ ] **GLD-F-02**: Time-of-day pattern analysis — identifies pods whose failure rate correlates with specific hours (thermal, scheduled tasks, network).
- [ ] **GLD-F-03**: Content drift detector — compares each pod's installed game/car/track inventory vs the expected pod TOML; alerts on drift.
- [ ] **GLD-F-04**: Concurrent session prevention — server-side guard: a single pod cannot have two active billing sessions or two active game launches even across kiosk + PWA + admin paths.

**Closes silent-loss points:** P2-09 (no concurrent-session guard), P2-10 (content drift invisible), P2-12 (per-pod intelligence missing).

### Phase 367 — Staff Tools (Phase G)

**Goal:** Give staff actionable UIs to triage suspect sessions and verify pods on demand.

- [ ] **GLD-G-01**: Admin `/admin/suspect-laps` page — lists all sessions flagged `suspect: true` by Phase C, with drill-down to per-lap telemetry heatmap.
- [ ] **GLD-G-02**: Admin on-demand pod verification — "Verify Pod N" button triggers a synthetic config-mismatch test (Phase B's deferred test) and returns pass/fail.
- [ ] **GLD-G-03**: Session replay — admin can replay any completed session's telemetry at 10× speed for QA review.
- [ ] **GLD-G-04**: Batch export — admin can export any date range's session data (billing + telemetry + laps) as CSV/JSONL for offline analysis.
- [ ] **GLD-G-05**: Retro-verification of GLD-B-03 WhatsApp alert path (deferred from Phase B).

**Closes silent-loss points:** P2-04 (no suspect lap view), P2-05 (no on-demand verify), P2-06 (no session replay), P2-13 (no batch export), P2-14 (no retro-verify path for Phase B alerts).
